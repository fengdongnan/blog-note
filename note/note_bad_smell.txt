## 命名

命名上, 用业务命名取代技术命名; 比如 books 替代 bookList
- 类似于 面向接口编程, 因为接口是抽象的, 而实现是易变的, bookList 未来也可能换为 Set 的实现, 如果没有留意字段命名则会留下历史歧义, 因此可以将字段名抽象为脱离数据结构的业务命名: books
- 此外业务命名也在倒逼 开发者 明确方法或字段的业务含义


类名通常为名词,表示对象; 方法名为动词, 或者是动宾短语，表示一个动作

DRY: 复制粘贴前的第一想法是先提取出函数，然后在需要的地方调用这个函数, 保持对重复的敏感


## 冗余编排

### 长函数

> 不知道你在实际工作中遇到最长的函数有多长，几百上千行的函数肯定是不足以称霸的。在我的职业生涯中，经常是我以为自己够见多识广了，但只要新接触到一个有悠久历史的代码库，就总会有突破认知的长函数出现。

编译器层面约束长函数

这不是一个说说就算的标准，我们应该把它变成一个可执行的标准。比如，在 Java 中，我们就可以把代码行的约束加到 CheckStyle 的配置文件中，就像下面这样：

<module name="MethodLength">
　　    <property name="tokens" value="METHOD_DEF"/>
　　    <property name="max" value="20"/>
　　    <property name="countEmpty" value="false"/>
</module>
　　这样，在我们提交代码之前，执行本地的构建脚本，就可以把长函数检测出来（关于 CheckStyle，我在《[10x 程序员工作法]》中讲[项目自动化]时专门做过介绍，你有兴趣不妨了解一下）。如果你用的是其它的程序设计语言，不妨也找一下相应的静态检查工具，看看是否提供类似的配置。

长代码产生的原因:
1. 业务代码平铺直叙, 没有做业务逻辑和细节层面的子方法分离;
2. 每次修改一点代码, 长期累计成为shishan代码

解决方法:
1. 每次编写代码时 做好逻辑的分离提取
2. 童子军军规: (永远保持营地比你发现它时更干净)每次提交代码时，都要让代码库的状态比你打开它时更好一点

### 大类

一个人理解的东西是有限的，没有人能同时面对所有细节。

人类面对复杂事物给出的解决方案是分而治之。所以，我们看到几乎各种程序设计语言都有自己的模块划分方案，从最初的按照文件划分，到后来，使用面向对象方案按照类进行划分，本质上，它们都是一种模块划分的方式。这样，人们面对的就不再是细节，而是模块，模块的数量显然会比细节数量少，人们的理解成本就降低了。

好，你现在已经理解了，对程序进行模块划分，本质上就是在把问题进行分解，而这种做法的背后原因，就是人类的认知能力是有限的。

理解了这一点，我们再回过头来看大类这个坏味道，你就知道问题出在哪了。如果一个类里面的内容太多，它就会超过一个人的理解范畴，顾此失彼就在所难免了。

大类产生的原因:
1. 职责不单一: 类中的字段对一部分实体是没有意义，但这些信息对于另一部分实体来说又是必需的。之所以会出现这样的状况，关键点就在于，这里只有“一个”实体类, 未按照职责进行拆分
2. 字段未分组: 同一实体下不同类型的字段可以再做抽取, 比如将用户类中的address, email 等抽取 Contract 实体类

### 长参数列表

函数间共享信息(传递参数)的两种方式:
- 参数列表
- 全局变量

1. 将参数列表封装成对象: 当参数具有共性时, 将参数抽取为一个参数类
2. 移除标记参数
3. 参数可以分为静态参数, 动态参数, 前者相对固定, 而后者则是频繁变更 --> 进行动静分离, 将静态参数作为函数所在类的一个字段, 入参只传递动态参数

## 控制语句
### if - else

解决方案: 抽取方法 + 卫语句（guard clause）

> 卫语句 是一种编程习惯，指的是在方法或函数的开头，优先检查异常情况、边界条件或前置条件。如果条件不满足，就立即通过 return（返回）或 throw（抛出异常）中断当前方法的执行。

  它的核心思想是：提前退出: 先处理掉那些不该走主流程的情况，让正常的核心逻辑留在最外层。

  在软件开发中，有一个衡量代码复杂度常用的标准，叫做圈复杂度（Cyclomatic complexity，简称 CC），圈复杂度越高，代码越复杂，理解和维护的成本就越高。在圈复杂度的判定中，循环和选择语句占有重要的地位。圈复杂度可以使用工具来检查，比如，在 Java 世界中，有很多可以检查圈复杂度的工具，我们之前提到过的 Checkstyle 就可以做圈复杂度的检查，你可以限制最大的圈复杂度，当圈复杂度大于某个值的时候，就会报错


idea 中设置检查圈复杂度:
1.idea setting -> Editor -> Inspections
2.Java -> Method metrics -> 勾选 Overly complex method
3.配置阈值, 提示级别

 ## 封装
 ### 火车残骸代码

即连续的函数调用: a.getB().getC().getD()

 未经封装, 直接取出字段, 将内部的实现细节暴露给外部:
 1. 对类本身, 实现细节暴露, 且存在 违反 OCP 原则的风险
 2. 对调用者, 需要跟进了解底层实现细节

 ```java
 　　String name = book.getAuthor().getName();
    //1.暴露了内部数据结果关系:Book -> Author -> Name, 如果后续改为多人合著, 模型变为 Book -> List<Author> authors, 则代码内所有的调用处都需要修改
    //2.写法上, 一连串取值容易 npe , 需要做特殊校验处理

    //解决方法: 隐藏委托关系
 class Book {

 　　  ...

 　　  public String getAuthorName() {
 　　    return this.author.getName();
        //return authors.stream().map(Author::getName).collect(joining(", "));
        //调用方只关心 book.getAuthorName()，只需在 Book 内部修改 ，外部调用方零感知、零修改
 　　  }

 　　  ...

 　　}
 　　String name = book.getAuthorName();
 ```

> 当你必须得先了解一个类的细节，才能写出代码时，这只能说明一件事，这个封装是失败的
> 要想摆脱初级程序员的水平，就要先从少暴露细节开始。声明完一个类的字段之后，请停下生成 getter 的手，转而让大脑开始工作，思考这个类应该提供的行为。

同时为了避免封装过于用力导致反方向坏味道:
- DTO这种纯数据流透传, 可以直接get
- 业务模型的字段透出, 必须做封装

### 基本类型偏执

用各种基本类型作为模型到处传递

重构方法: 以对象取代基本类型，也就是提供一个模型代替原来的基本类型

```java
    public double getEpubPrice(final boolean highQuality, final int chapterSequence) {

　　  ...

　　  }
    //方法返回价格, 这里用 基本类型 double, 不具有业务含义
    //但是 价格 作为一个实体拥有自己的业务含义, 比如 "价格>0", "对外呈现时只有两位"

    　　  private long price;

    　　  public Price(final double price) {  //构造时限制大于0, 否则需要在各种用到的地方做判断

    　　      throw new IllegalArgumentException("Price should be positive");
    　　    }
    　　    this.price = price;
    　　  }

         public double getDisplayPrice() {   //将项目中散落的转换逻辑收敛到实体内
         　　  BigDecimal decimal = new BigDecimal(this.price)；
         　　  return decimal.setScale(2, BigDecimal.ROUND_HALF_UP).doubleValue();
         　　}
    　　}

```


 ## 可变数据

 程序 = 数据结构 + 算法; 但是软件 = 众多程序的组合, 因此需要使用 设计模式和抽象思想 来维护使用

 setter 同 getter 一样，反映的都是对细节的暴露。

 可变数据最直白的体现就是各种 setter。setter 一方面破坏了封装，另一方面它会带来不可控的修改，给代码增添许多问题。解决它的一种方式就是移除设值函数（Remove Setting Method）, 为变换参数抽象方法, 将变化限制在一定的范围之内。

可变数据是《重构》第二版新增的坏味道，这其实反映了软件开发行业的一种进步，它背后的思想是函数式编程所体现的不变性。解决可变数据，一种方式是**限制其变化**，另一种方式是**编写不变类**。


## 变量声明与赋值

变量的初始化是分成了声明和赋值两个部分, 如果分开实现则代码不清晰，**变量初始化与业务处理混在在一起**, 最好一次性完成

在能够使用 final 的地方尽量使用 final，限制变量的赋值

集合的初始化:
```Java
List<Permission> permissions = new ArrayList<>();//1

　　permissions.add(Permission.BOOK_READ);//2
　　permissions.add(Permission.BOOK_WRITE);//3

　　check.grantTo(Role.AUTHOR, permissions);
```
1是列表声明, 2,3是赋值, 1,2,3合起来才是入参列表的初始化, 两种改法:
- jdk 9 之后: List.of()
- 之前: ImmutableList.of() Guava提供, 用于创建不可变集合, 效率比ArrayList更高

命令式/生成式代码
- 命令式的代码，就是告诉你“怎么做”的代码，就像改造前的代码，声明一个集合，然后添加一个元素，再添加一个元素。
- 而声明式的代码，是告诉你“做什么”的代码，改造后就是，我要一个包含了这两个元素的集合。

## 依赖
今天我们讲了由于代码依赖关系而产生的坏味道，一种是缺少防腐层，导致不同代码糅合在一起，一种是在业务代码中出现了具体的实现类。

缺少防腐层，会让请求对象传导到业务代码中，造成了业务与外部接口的耦合，也就是业务依赖了一个外部通信协议。一般来说，业务的稳定性要比外部接口高，这种反向的依赖就会让业务一直无法稳定下来，继而在日后带来更多的问题。解决方案自然就是引入一个防腐层，将业务和接口隔离开来。

业务代码中出现具体的实现类，实际上是违反了依赖倒置原则。因为违反了依赖倒置原则，业务代码也就不可避免地受到具体实现的影响，也就造成了业务代码的不稳定。识别一段代码是否属于业务，我们不妨问一下，看把它换成其它的东西，是否影响业务。解决这种坏味道就是引入一个模型，将业务与具体的实现隔离开来。

简单的依赖关系，可以通过自动化工具来进行维护，比如 ArchUnit。

## 代码评审
代码评审意义:
- 运用集体智慧对个人代码进行审查
- 将个人知识暴露到团队层面做共享

代码评审实践:
- 评审角度: 代码评审可以从实现方案正确性、算法正确性和代码坏味道的角度去发现问题
- 评审频率: 越高越好, 控制在一个迭代 or 一天一次, 尽早暴露问题避免积少成多

##
接口的新增要谨慎: 能不能用已有接口复用逻辑 提供实现, 而不是新加接口
实体: 不要轻易修改属性, 实体应该保证稳定性, 当出现需要添加字段的情况考虑 单一原则 拆分实体

对于接口，我们对外提供得越少越好，而对于实体，我们必须仔细分析它们扮演的角色。
