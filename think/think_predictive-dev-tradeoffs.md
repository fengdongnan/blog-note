## 问题本末

在接到产品的需求进行开发时, 经验老道的开发人员会去预测评估需求的未来延展性, 从而在当前需求的开发中进行一些预测增量开发去预备未来可能会有的需求变动.

比如要在toc 系统上新加一个qa功能, 给用户提供一个意见反馈入口. 第一期功能只需做用户的意见提交, 以及b端的意见查看这样一个最简单的链路; 那么在设计库表时, 考虑到后续需求第二期时会在管理端添加工单的处理流程, 那么就要在表中预留 工单处理人, 工单状态等字段, 这样后续做需求迭代时不需要再去修改db 表结构新增字段.

但是每个需求都要做这种预测设计吗? 是否会造成冗余设计吗?

当下有一个需求是根据标签id返回其相似标签列表,且对返回结果进行去重; 上游 rpc 接口返回的结构是 Map<入参标签id, List<相似标签>>, 打平后返回给前端 List<相似标签VO>. 相似标签vo只包含标签id, name;

考虑到未来可能会要求展示 推荐项具体是哪个节点的相关推荐, 可以在返回的vo中添加归属节点id, 但两个归属id的推荐列表可能会有交集, 那么这些重叠项的归属id怎么处理呢? 是取一个还是都去, 这都是需要拉产品去额外确认的内容, 带来的是一个新的需求分支与考虑项目. 最终还是打回了这个想法, 只做本期内容, vo只返回 id, name.

## 预测性开发的取舍

个人总结出一个准则, 就是 预测性开发的前提是不要给当前需求的开发增添过大的开发负担.
比如之前的qa功能的字段预估, 付出只是写建表sql语句和后续的 BO实体 添加 两个字段, 带来的好处是后续不需要提一堆工单和经历繁琐的审批周期去修改表字段, 这个收益比是可取的. 第二个例子则是引入了新的未知业务忙点和开发任务, 这无疑是一种负担(并且未来可能都不会为这个边角的小选择框做这个功能) . 如果为了预测设计反而需要在当下为其考虑设计处理逻辑, 甚至这个功能未来不是100%会做, 那就是本末倒置, 得不偿失

实施上 ai 总计的更具体: 
预测性开发评估表

| 评估维度 | 推荐做法（Do） | 避坑/禁止（Don't） | 核心判断依据 |
| :--- | :--- | :--- | :--- |
| **1. 变更成本比 (ROI)** | **预留数据与接口定义**<br>• DB Schema 字段<br>• Protobuf / RPC 拓展字段 | **提前书写业务代码逻辑**<br>• 提前写 Service 方法<br>• 提前增加业务分支 | **看变更成本：** 生产环境变更成本高（锁表、接口兼容、上线顺序）才值得预留；业务代码部署成本低，随用随改。 |
| **2. 形态：结构 vs 逻辑** | **预留结构（架构留白）**<br>• DB 加索引 / 字段<br>• API 返回拓展 Map（`ext_info`）<br>• 使用策略 / 责任链模式 | **提前实现逻辑（过早演化）**<br>• 提前计算并缓存未用数据<br>• 写 `if (futureFeature)` 分支<br>• 搞复杂的预判去重 / 排序 | **“结构可预留，逻辑当下做”：** 只留扩展槽位与设计弹窗，绝不在当前迭代提前运行未来的业务计算。 |
| **3. 业务确定性 (P%)** | **高确定性需求（P > 80%）**<br>• 提交 → 审核/处理<br>• 订单创建 → 支付/退款<br>（主干链路做结构预留） | **低确定性需求（P < 30%）**<br>• 产品说不清的细化展示<br>• 边缘场景逻辑（如节点重叠）<br>（按 **YAGNI 原则** 当下砍掉） | **看发生概率：** 主干必然演化的链路可以预留；概率低或细节不明确的边缘需求，绝不为假想场景买单。 |

> 敏捷开发中 **YAGNI 原则（You Ain't Gonna Need It - 你不会需要它）**
## 总结

预测性开发 要的是通过提前设计减少总工作量, 而不是将未来的可能工作量提取到现在来做.
